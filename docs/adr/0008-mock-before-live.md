# ADR-0008：Mock 先行，把闭环跑通再接真系统

## 背景

修复闭环依赖三个外部系统：观测平台（只读）、回放服务、优化器（异步任务）。其中两个在联调期不稳定或尚未部署，而每次真实验证都有成本与副作用。

## 备选

1. 等三个系统都就绪再开发；
2. 先写代码，联调时再补；
3. 先做三个脚本化替身，按契约把闭环跑通，再逐个替换为真实实现。

## 决定

选 3：

- 替身实现**真实 HTTP 接口**，不是内存函数调用——契约问题必须在联调前暴露；
- 优化器替身实现异步任务语义：202 + `task_id` + 轮询终态；
- 回放替身按"冻结主键 + 新提示词"返回确定性结果；
- 平台侧所有传输都是注入点，生产、测试、demo 共用同一套路由与账本。

## 代价

- 替身本身要维护；
- 替身通过不代表真实系统通过，联调仍然必须做；
- 需要克制"把替身做成万能模拟器"的冲动。

## 为什么

- 闭环的价值在状态机与口径，不在某个具体外部接口；
- 脚本化替身让每个失败分支（拒收、2/3、预算耗尽）都能被演示和测试；
- 接口契约先行的成本，远低于联调时才发现"字段名对不上"；
- 真实系统不可用时，demo 仍然可运行——这本身就是工程能力。

## 证据

本仓库的 demo 就是这套替身的公开版本：三个服务独立端口、真实 HTTP、确定性脚本。真实项目里同一套注入点也用于测试，路由与落库始终是真实代码。
