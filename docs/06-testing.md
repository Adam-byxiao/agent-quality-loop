# 测试：把"不可重跑"的系统做成可重跑的

内部版有 1,254 个测试（约 2 万行），覆盖后端、前端类型检查与浏览器端到端。这里讲的不是数量，是分层和替身策略——因为这套系统天生依赖不可控的外部服务。

## 分层

| 层 | 测什么 | 怎么测 |
| --- | --- | --- |
| 纯函数 | 报文归一、评分聚合、轨迹对齐、报告口径 | 直接调用，无 IO；边界值比正常值多 |
| 账本 | 迁移、幂等、指纹去重、状态流转 | 临时 SQLite；同一套用例可选跑 MySQL |
| API | 鉴权、CSRF、错误码、冻结/启动/停止 | `httpx` 直连 `create_app`，注入传输替身 |
| 编排 | 尝试循环、预算、拒收、重测、回归 | 注入脚本化的优化器/回放传输，固定时钟 |
| 浏览器 | 关键路径真正点一遍 | 隔离实例 + 独立数据库，不碰真实项目 |

## 三个替身原则

### 1. 外部服务全部可注入

`create_app(...)` 接受 `optimizer_transport / replay_transport / observability_transport` 等注入点。生产走真实 HTTP，测试与 demo 走替身，**路由、鉴权、落库始终是真实代码**。

这条原则的收益：编排的每个分支（拒收、2/3 失败、预算耗尽、人工停止）都能被测试，而不是只在文档里存在。

### 2. 替身是脚本，不是随机

同一个输入永远得到同一结果：

- 第 1 次提案返回含不可验证字段的候选；
- 第 2 次返回会 2/3 失败的候选；
- 第 3 次返回 3/3 通过的候选；
- 回放的 trial 序号决定该次通过与否。

随机失败的测试只会制造 flaky，不会证明鲁棒性。真正的抖动应该在**验证逻辑**里被吸收（3 次回放），而不是在测试里制造。

### 3. 时间与并发要显式

- 轮询间隔、租约过期、TTL 都通过参数注入，测试里设为 0 或固定值；
- 后台执行器在测试中同步执行或等待明确事件，不靠 `sleep` 猜；
- 幂等用"同一 task_id + 原样请求体"再提交一次来验证，而不是信任注释。

## 值得单独测的口径

普通 CRUD 的测试价值有限，真正容易错、错了又看不出来的是口径：

| 场景 | 断言 |
| --- | --- |
| 同一观测两行评分 0 和 1 | 结果为 `uncertain`，不是 0.5 |
| 不同观测一行 1 一行 0 | 该轮失败 |
| 评分值为 0.5 | `uncertain`，不映射成通过 |
| 候选含 `tool_description` | 拒收，且**回放调用次数为 0** |
| 回放 2 次通过 1 次失败 | 不接受，资产序号不变 |
| 无 replay_key | 冻结为 `skipped`，不出现在回归分母 |
| 扫描被截断 | 报告的覆盖数字与实际读取条数一致 |
| 批次被停止 | 终态 `stopped`，不是 `converged` |

## demo 的验证方式

demo 把外部调用集中在 `runner.py` 的传输函数里，路由与落库仍然是真实代码；三个替身是独立的 HTTP 服务。端到端检查用一条命令：

```bash
python demo/scripts/smoke.py
```

脚本会拉起替身与平台、创建批次、等待终态，并断言 `converged`、资产 `seq 1→2`、回归 `8 passed / 1 excluded`，以及"不可验证改动在回放前被整份拒收"。
