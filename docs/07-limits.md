# 边界：主动写清楚没做到什么

一份只写能力的文档没有信息量。这一页列出真实的限制与取舍，以及为什么暂时不修。

## 能力边界

| 限制 | 影响 | 为什么不修 |
| --- | --- | --- |
| **只接受主提示词候选** | 技能、工具描述、参数描述的改动无法被回放验证，整份拒收 | 回放服务只替换主提示词；放开等于制造"假通过"。需要上游支持完整候选注入 |
| **不可回放的失败永久不可验证** | 早期流量没有回放主键，只能统计、报告、人工修 | 上游不回填，平台不伪造近似重跑 |
| **会话扫描有上限** | 大窗口会截断，只处理最近 N 条 | 上游无全量接口；界面必须提示"未读完" |
| **单实例执行** | 重启中断批次；不能水平扩容 | 需要租约/选主；当前是明确的下一步，不是已完成 |
| **异步任务终态 600 秒** | 拉取器停摆超过窗口只能得到 `expired` | 对端契约限制；平台不能假装成功 |
| **单次整集回归** | 回归本身也有抖动 | 可配置多次；默认一次是成本与信心的折中，报告写明 |
| **逐条串行** | 大批次耗时长 | 并发会引入资产竞争：两条同时接受候选，谁做下一轮起点？先串行再考虑隔离 |

## 部署边界（内部版）

- 内网 HTTP，没有 TLS；上公网前必须加证书、secure cookie 并重核 Origin 白名单；
- SQLite 为默认存储，MySQL 需要手工执行迁移；两套 DDL 必须同步；
- 反向代理后必须显式开启可信代理，否则登录限流退化。

## demo 的边界

demo 是**能力切片**，不是产品：

- 没有登录、多项目、权限、审计；
- 没有真实外部系统，只有脚本化替身；
- 没有分享、凭据加密、出站策略的实现（文档描述的是设计，不是 demo 代码）；
- 数据与业务域完全虚构。

## 一个反直觉的结论

把限制写进产品，不是减分项：

- `skipped` 被点名，团队才知道这类缺陷永远无法自动验证；
- `stalled` 不等于"接近成功"，预算决策才有依据；
- 报告写"未验证技能改动"，才不会被下游误读成"已经改好了"。

**平台的价值不是让数字好看，是让结论可信。**
