# 问题定义：Agent 评测平台容易"看起来对"

## 三个不对称

做 Agent 质量平台，最先要承认的不是"功能很多"，而是三件事天生对平台不利。

### 1. 真实轮次有副作用，不可随便重跑

一次真实对话会在业务系统里创建会话、锁库存、发通知。平台不能像单元测试那样"再跑一遍看看"。于是所有验证都必须建立在**已经发生过的证据**上：

- 失败轮次必须能定位到一次具体的模型请求（可回放主键）；
- 回放只能替换**一个**可变部分，其余（历史、工具定义、技能正文）必须原样冻结；
- 没有冻结主键的失败轮次，永久不可验证——平台应该明说，而不是用一个"近似重跑"冒充。

### 2. 判定权不在平台手里

评分通常由另一套系统产生（人工、规则或另一个模型）。平台如果重新判分，就会和团队实际看的分数不一致；如果对冲突评分取平均，就会发明一个谁都没做过的判断。

可接受的做法只有一条：**读现有评分，按明确的聚合规则判定，判不了就记 `uncertain`。** `uncertain` 不是通过，也不是失败，是"没有判定"。

### 3. 覆盖范围天然残缺

上游观测平台可能没有轨迹索引、不返回总数、静默忽略筛选参数、只允许按页扫描。平台能看到的永远是一个**窗口**，不是全集：

- 扫描了 100 条观测，不代表只有 100 条；
- 深采样了 12 条 token 数据，不能代表整体分布；
- 分位数用实际观测值计算，被截断时会**低估**，必须标注。

## 常见的三种"造假"

| 看起来对 | 实际上 |
| --- | --- |
| 候选提示词"跑了一次通过" → 记 verified | 单次回放会抖动，通过一次不等于稳定 |
| 冲突评分 0 和 1 → 取 0.5 记 "部分通过" | 这是平台发明的判定，掩盖了真实分歧 |
| 概览页显示"平均耗时 15.8s" | 混合了 Agent 与评分器，既不描述前者也不描述后者 |

这三种都不是 bug，是**口径错误**。口径错误比崩溃更难发现，因为它看起来一直有数字。

## 设计回应

本项目的全部结构都可以从上面三条推导出来：

| 约束 | 机制 |
| --- | --- |
| 不可重跑 | 冻结失败轮次：评分证据、历史、回放主键、起始资产快照 |
| 判定权不在平台 | 只读评分 + 一致才判定 + `uncertain` 一等公民 |
| 覆盖残缺 | 每一层标注覆盖范围；被排除的对象在报告里点名 |
| 候选可能无法验证 | 候选字段白名单：不能注入回放的改动整份拒收 |
| 单次验证不可靠 | 三次独立回放，3/3 才接受 |
| 修复可能引发回归 | 接受后重测剩余失败，结束时整集回归 |

## 边界

这套设计假设：平台**不负责训练模型、不负责发布提示词**。它只做一件事——把失败变成证据，把候选变成可验证的结论，把结论写清楚。发布由人决定。
